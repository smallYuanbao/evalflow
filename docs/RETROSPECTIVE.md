# EvalFlow 复盘

> 一份给面试用的项目叙事。不是功能清单——是「为什么这么做」和「踩过什么」。

## 一、30 秒版

**EvalFlow 是一个 RAG/LLM 评测平台。** 你给它一个评测集(问题 + 期望要点 + 分桶)，
它跑评测、算指标、给 PASS/FAIL 门禁判定，并把「这次比上次好不好、为什么」讲清楚。

它最大的特点不是我写了多少功能，而是——**它评测的对象后来换成了我自己做的另一个 RAG 应用**。
这件事把评测平台的价值从「嘴上说」变成了「实测出来」：接上真实系统后，**并发评测逼出了对方一个
潜伏的并发 bug，评测平台自己也被发现有指标判错**。

（27 章，后端 92 测试 / 前端 33 测试 / Playwright e2e 全绿。）

---

## 二、主线：评测平台的价值不在「算出分数」

**任何一个能调 LLM 的人都能写出「跑一遍、打个分」的脚本。** 那不算平台。

平台的价值在于让分数**可比、可信、可行动**——这三件事，每一件都比「算分」难一个量级。
整个项目就是这个主线的展开。

### 1. 可比 —— 分数必须能横向纵向比

一个分数如果不知道「它是在什么条件下算出来的」，就没有意义。

- **快照机制(Ch09)**：发起评测时把「复现上下文」写进 run——
  知识库版本与哈希、prompt 版本、生成/嵌入模型、数据集哈希、top_k、检索方式。
  历史 run 不受后续改动影响。
- **版本化迁移(Ch14)**：SQLite → PostgreSQL 可切换 + alembic 接管建表，
  存量库用 `stamp head` 收养。**不换默认值**——本地仍 SQLite，零改动。
- **跨系统可复现(Ch26)**：接 baby-ai 后发现一个关键问题——**可复现性有一半在对方系统里**。
  EvalFlow 只记自己这半边，则「这次比上次好」不成立(可能是对方知识库变了)。
  解决办法是让对方暴露 `/api/meta`，把它的版本/模型/检索配置/知识库规模也记进快照。
- **拿不到就显式说「不知道」**：meta 不可达时快照写 `meta_error`，
  详情页警示「本次结果**不可**与历史对比」。
  **静默记空比不记更危险**——它会让人误信可比。

### 2. 可信 —— 指标和裁判本身也要被检验

这是项目里我最看重的一层：**「分数的分数」**。

- **judge 校准(Ch18)**：LLM 当裁判打的 0.8 分凭什么信?人工标金标准 → 对比 →
  出 **bias(系统性偏松/偏严) / MAE / Pearson / n**。bias 最可操作(能直接指导修正)。
- **judge 方差(Ch20)**：多次采样后把方差也存下来，识别「不稳定裁判」。
- **可解释性(Ch18)**：每个分数都能下钻到「证据 + 裁判给的理由」。
- **拒答识别(Ch27)**：库外题靠关键词表机械判定。接 baby-ai 后发现——
  **它明明拒答了，但措辞是「不在我的专业范围内」，词表一个都匹配不上**，判成「没拒答」。
  这是**评测平台自己的缺陷**，评自己的 toy pipeline 永远遇不到(那些回答是我们自己写的，
  措辞天然贴着词表)。

> **「用自己的数据测自己的规则」是自欺**——规则和数据同源，测不出覆盖不足。
> 而且这类失效是**静默的**：不报错，只是分数错。

### 3. 可行动 —— 从「一堆数字」到「一个决定」

- **回归门禁(Ch15)**：绝对阈值(`faithfulness ≥ 0.7`)+ 相对基线回归(较基线最多掉 0.05)。
  两条腿挡「绝对质量差」和「改坏了」。null 指标记「未评」不通过——门槛是「每个指标都得评上且达标」。
- **分桶归因(Ch19)**：门禁说「掉了」，归因说「是库外题掉的」。
- **逐条 Diff(Ch18)**：归因说「库外题掉了」，Diff 说「是『宝宝拉肚子怎么办』这一条」。
- **模型性价比(Ch19)**：把分数和成本摆一起，回答「贵 20 倍值不值」。
- **一键复跑(Ch20)**：按快照重跑，把「可复现」从声明变成按钮。

**这条链**：整体分数看不出问题 → 分桶归因缩小范围 → 逐条 Diff 锁定到具体样本。
这是「可行动」的完整形态。

## 三、三个项目的关系

| 项目 | 角色 | 技术亮点 |
|---|---|---|
| **MewHelp**(电商客服) | Agent 编排 | LangGraph 状态机、**Milvus**、多 MCP Server、微调分类器、LangFuse |
| **baby-ai**(育儿助手) | RAG 管线 | 意图路由 → **混合检索** → 精排降级 → 生成、SSE 流式 |
| **EvalFlow**(本项目) | 评测量化 | 数据集管理、LLM-as-Judge、门禁、归因、可复现 |

**闭环**:做 Agent(MewHelp)、做 RAG(baby-ai)、**再做评测量化它们(EvalFlow)**。
Ch26 把 baby-ai 真正接到了 EvalFlow 上——从「三个并列项目」变成「一个闭环」。

**一个差异化钩子——混合检索我做过三遍，三种实现**:

| 实现 | 在哪 | 特点 |
|---|---|---|
| **Milvus** | MewHelp | 生产级向量库，原生 dense + sparse + hybrid search |
| **chroma + RRF** | baby-ai | 应用层融合，轻量 |
| **手写 BM25 + RRF** | EvalFlow Ch16 | 从公式写起，最轻、最透明 |

面试里能讲清「生产级向量库 vs 应用层融合的取舍」，这是大多数候选人给不出的对比。

**方法论也是同源的**:三个项目都用同一套「先写 spec(决策) → 再写 plan(Task 列表) → 实施 → 同步回文档」，
`docs/superpowers/` 就是这套流程的产物。

## 四、最能讲的四个发现

**都是「接真实系统」才暴露的，评自己的 toy pipeline 一个都遇不到。**

### 1. 并发评测逼出对方一个潜伏的并发 bug

改 baby-ai 一个配置想对比指标，结果**第二次评测直接失败**。日志精确指向
`retriever.py:144` `IndexError`。

对照实验:关改写会挂、**开改写并发也挂** → 证明**跟配置无关**，是早就存在的 bug:
BM25 懒加载非线程安全，并发请求同时看到「还没初始化」就各自跑一遍，
一个线程重建索引数组时另一个正在用它索引。

**手工单点试用永远不会暴露**——只有并发评测会。

### 2. 测出了被测系统的真实短板

baby-ai 的 `faithfulness` 只有 **0.1**。逐条看 trace，它自己都写着
「以下回答基于我的**通用医学知识**」「知识库中**没有相关信息**」——
**检索到了证据却不用它**。这正是 RAG 评测该抓的问题。

### 3. 发现评测平台自己判错了

`rejection` 判 0.0，但人工看 trace 发现 baby-ai **明明拒答了**——见上面「可信」一节。

修的过程还有个反复:第一版词表写「**我**只能回答」，下一跑 baby-ai 说成
「**只能回答**育儿相关问题」(少了个「我」)，**照样漏**。
> 同一个模型换个 run 措辞就会漂，**词表不能贴着某一次的输出写**。

### 4. 导出 CSV 的内存爆炸

样本少时一切正常。算一下才发现：后端把全量 trace + 整份 CSV + 加 BOM 的副本存了 2~3 份，
前端又是 axios 字符串 + Blob + objectURL 再 2~3 份。
**一份 100MB 的 CSV，前后端合计吃 400~600MB。**

改法：后端 `StreamingResponse` + `yield_per`，前端**交给浏览器原生下载**(不碰 JS 内存)。

> 关键判断:**「先攒齐再交付」在数据规模不受控时必然出事**。
> 判据很具体——响应头有 `transfer-encoding: chunked` 才是真流式。

## 五、一条被「用出来」的演进：从界面钻到测量方法

Ch24 之后有一段连续的问题，值得单独讲——因为它展示了**提问深度的爬升**：

| 阶段 | 问的是什么 | 挖出了什么 |
|---|---|---|
| Ch24 | 输入框布局、标签含义 | 分桶不是分组标签，是**评分语义的开关** |
| Ch25 | 数据多了还能下载吗 | 「先攒齐再交付」是内存的敌人 |
| **Ch26** | **能不能评真实系统** | **分水岭**——并发评测逼出对方一个潜伏的并发 bug |
| Ch27 | 它明明拒答了，为什么判 0 分 | **评测平台自己判错了** |
| Ch28 | 阈值 0.7 有什么依据 | **两个方向都错**：高于被测系统实际水平、低于噪声 |
| Ch29 | 这两次 run 真的可比吗 | 评测集改过 → **分数不可比，而门禁不说** |
| Ch30 | 裁判能不能换 | 生成和裁判共用配置 → **做不了 A/B** |
| Ch31 | 分数基于几条？尺子准不准？ | 覆盖率不可见 + **校准机制建了从没用过** |

**分水岭是 Ch26。** 在那之前，问题都在「界面层」；接上真实系统之后，问题开始指向**评测方法本身**。

### 后五章的共同主题：怀疑自己的测量工具

- **Ch27**：关键词表匹配不上真实系统的措辞 → **规则和数据同源就测不出覆盖不足**
- **Ch28**：换裁判指标动 0.31，而门禁容忍度只有 0.05 → **先量准仪器，再用它下结论**
- **Ch29**：评测集改过，`dataset_id` 没变但内容变了 → **前提不成立时系统必须说出来**
- **Ch30**：换裁判要连生成一起换 → 裁判是**仪器**，必须能单独换、单独记
- **Ch31**：分数不说「基于几条」；校准机制建了却没用过 → **尺子准不准，得亲自验**

这五条都**不是「我实现了什么功能」**，而是「**我发现我的测量方式本身有问题**」。

### 一个具体的收获：校准揭示的东西

我第一次真正用「人工金标准」验了自己的裁判（Ch31，16 条人工打分）：

| 指标 | bias | Pearson |
|---|---|---|
| faithfulness | **−0.138** | 0.549 |
| answer_correctness | **+0.106** | 0.929 |
| answer_relevance | +0.016 | **0.978** |

**两个结论直接改变了设计判断**：

1. **偏差按指标分方向** → 「加一个统一修正量」是错的；
2. **偏差在「比较」中抵消、在「绝对值」中不抵消** → **回归门禁比绝对阈值可信**。

还有个小样本的实证：`answer_relevance` 的相关系数 **n=8 时 0.315，n=16 时 0.978** ——
我早先就写过「小样本的极差有 50% 误差」这个警告，这次是它自己撞上来了。

### 评测平台逼出的东西：baby-ai 的四个真 bug

这是我认为**整个项目最有说服力的部分**——不是「我写了什么」，是「**我的东西让别人变好了**」：

| 怎么发现的 | baby-ai 的问题 |
|---|---|
| 并发评测 | **BM25 懒加载非线程安全** → 服务刚起时并发请求整批 500（手工单点试用永远不会暴露） |
| 读数据准备校准 | **空回答的四层级联**：模型失败 → 空答案进缓存 → 同题永远返回空 → 空答案进会话历史 → 该会话永久 500 |
| 同上 | **max_tokens 太小**：模型换成推理模型，预算还是给非推理模型定的 → 思维链吃光预算 → content 为空 |
| 改配置做 A/B | 限流按 IP 不按用户 → NAT 后多用户互相抢额度 |

那个四层级联尤其能说明问题：**四层里少查任何一层，都只会看到表象**
（缓存命中 / 服务不稳定 / 偶然空回复）。而且我自己中途还修得不够彻底
——第一次只拦了「空回答」，没拦「降级兜底文案」，又补了一次。

### 为什么这段在面试里特别值钱

> 一个能写出评测平台的人，和一个**能发现自己评测平台在骗人**的人，不是一个层次。

前者的坑是「做不出来」；后者的坑是「**做出来了但结果是错的，而且不报错**」。
后者更难发现——因为测试全绿、指标算得出来、界面一切正常，
**只有穷究「这个数字凭什么可信」才会暴露**。

而且每一次都是**先怀疑、再实测、最后改掉**：
- Ch27：用 baby-ai 的**真实回答原文**做用例（而不是编一个贴着词表的句子）
- Ch28：先测三个噪声源，再据实校准（而不是继续沿用 0.7）
- Ch31：先修掉 baby-ai 的 bug 拿到干净数据，再人工打分（而不是拿脏数据校准）

**面试时的讲法**：
> 「平台跑起来之后，我没停在『指标能出来』，而是继续问『这个指标凭什么可信』。
> 结果一路挖出五件事——我的拒答识别认不出真实系统的措辞；我的门禁容忍度比测量噪声还小，
> **它天天在误报而我一直以为它在正常工作**；两次 run 的评测集其实不可比；裁判换不了所以验不了；
> 最后我亲手标了 16 条金标准，才发现裁判对『忠实度』系统性偏严 0.14。
>
> 顺带，这套东西在真实系统里逼出了四个 bug，其中一个是四层因果链——
> 少查任何一层都只会看到表象。」

## 六、诚实的边界：没做什么，为什么

面试里说清「不做什么」和「为什么」，比列功能更能体现判断力。

| 没做 | 为什么 |
|---|---|
| **SSE 实时进度** | 进度是 Celery worker 写的，要真推送得跨进程上 Redis pub/sub。为「一个进度百分比」不值得；1.5s 轮询够用。**能讲清「为什么这里用轮询而不是 SSE」比真写一段更有价值。** |
| **统计显著性 / 置信区间** | 已识别为必要(5 个样本上 ±0.1 基本是噪声)，但 demo 数据量下用不上。**知道它该做、也知道现在不该做。** |
| **CI 自动评测 + PR 门禁** | 需要 remote + CI 跑真实 LLM(密钥/成本)，且仓库无 remote。工作流已写好待用。 |
| **多租户 / 权限角色** | roadmap 明确排除——Ch12 只做单用户 API key，先解决「防匿名烧钱」。 |
| **Agent 评测** | 见下——**最值得展开的一条「没做」** |

### 展开：为什么没做 Agent 评测

这是「诚实的边界」里最值得讲的一条，因为它**不是「没时间」，是「想清楚了不该做」**。

#### 分水岭:标准答案从「一段文本」变成了「一条路径」

| | 单轮 QA | Agent |
|---|---|---|
| 标准答案 | 「物理降温/就医/用药」——**可穷举** | 「该走哪些步骤」——**不唯一** |
| 评测方式 | 逐要点比对 | **没法逐步比对** |

「订单 1001 到哪了」至少有两条路径都对:直接查物流,或先查订单拿运单号再查物流。
**所以你写不出「标准轨迹」。** 只能退而求其次:

- **只比工具集合**(MewHelp 的选择)——放弃顺序,放弃「多调一次算不算错」;
- **让 LLM judge 评轨迹**——引入裁判不确定性(而 Ch28 已经证明裁判方差有 0.3 量级)。

#### 五个难点(按根本性)

| # | 难点 | 说明 |
|---|---|---|
| 1 | **标准路径不唯一** | 见上——这是分水岭,其余四点都由它派生 |
| 2 | **标注成本线性增长** | 单轮标一条 = 写几个要点;Agent 标一条 = 写「该调哪些工具」,还要覆盖多类意图 × 多种问法 |
| 3 | **轨迹长度不定,怎么聚合** | 步数少≠好(可能偷懒),多≠差(可能严谨);「平均步数」意义存疑 |
| 4 | **成本与延迟升为一级问题** | 多步 = N 次 LLM。评 20 条 Agent 任务 ≈ 评 100 次单轮——**评测本身的成本成了新问题** |
| 5 | **失败模式变多** | 工具选错 / 参数错 / 循环不终止 / 中间对但最终错 / **工具服务本身挂了** |

#### 调研后的结论:不做,而且理由不是「没时间」

调研中发现两件事,直接改变了判断:

1. **MewHelp 已经有 Agent 评测了** —— `eval_agent.py`,8 条标注样例 + 核对工具选择;
   而且 `POST /api/agent` **已经返回 `tool_calls`**,轨迹数据是现成的。
2. **MewHelp 自己就有一整套评测**(14 个 `eval_*.py`:分桶检索、意图 P/R/F1、置信度校准、
   评估流水线 + `/rag-eval` 页面)——**某些方面比 EvalFlow 更成熟**。

所以「EvalFlow 做 Agent 评测」的真实增量不是「补一个能力」,而是
**「把 MewHelp 那十几个脚本统一到一个平台」——那是重构 MewHelp,不是给 EvalFlow 加东西**。
投入一整章,产出一句「EvalFlow 也能评 Agent 了」,不成比例。

#### 但这段本身是面试答案

> **「Agent 评测难在哪」——想清楚为什么不做,比做出来更值钱。**

具体讲法:
> 「我做的是单轮 QA 评测。有人会问为什么不评 Agent——我想过,而且**调研后决定不做**。
> 难点不在工程量,在**标准答案从一段文本变成了一条路径,而路径没有唯一正确答案**。
> 我看了同域的另一个项目怎么处理:它退而求其次,**只比工具集合**,放弃顺序和次数。
> 这是个合理的工程妥协,但你要知道**妥协掉了什么**。」
>
> 「而且它自己已经有一整套评测脚本了,我再做一遍是重复造轮子——
> 真正的增量是把那套东西统一到平台里,那是重构它,不是给我加功能。」

**知道理想方案和工程妥协的分界线在哪,比选了哪一边更重要。**

### 展开：和 MewHelp 的评测比，差在哪、吸纳了什么

MewHelp **自己有一整套评测**（14 个 `eval_*.py` + `/rag-eval` 页面），某些方面比 EvalFlow 更成熟。
把两边摆在一起看，能讲清楚「脚本式评测」和「平台式评测」各自的强项。

#### 两种范式

| | MewHelp | EvalFlow |
|---|---|---|
| 形态 | **脚本式**（Makefile 目标 + 落 JSON） | **平台式**（数据集 → run → 指标 → 门禁） |
| 强项 | **评测集的严谨设计** | **run 的生命周期管理** |
| 产物 | `.txt`（人读）+ `.json`（页面读） | 数据库里的 run/trace/score |

#### EvalFlow 领先的部分

- **快照 / 可复现**：MewHelp 的产物是 JSON，没有「这次用的哪版知识库/prompt/模型」的概念；
- **门禁**：MewHelp 产出指标表，**没有通过/不通过的判定**；
- **裁判校准**：它有 `calibrate-confidence`，但校的是**置信度阈值**（业务阈值），不是**裁判准不准**；
- **通用性**：EvalFlow 换过被测系统（toy pipeline → baby-ai），它的脚本绑死自己的管线。

#### MewHelp 领先、值得吸纳的部分

**① 评测集自检（`eval-check`）——已吸纳为 Ch32**

它的原话：「300 题手写的 ground truth **靠这个脚本兜住，不靠人眼**」。
查的关键一条是:**`expect_points` 必须逐字出现在知识库正文里**——
因为覆盖度是机械子串匹配,**要点写得再对、只要库里不是这么写的,分数就永远上不去**。

**EvalFlow 有完全相同的风险**（`recall` 也是子串匹配）**却完全没有防护**。
于是照它的思路做了 `GET /datasets/{id}/validate`,第一次跑就抓到了真问题:

| 题 | 期望要点 | 证据里的实际措辞 |
|---|---|---|
| 宝宝吐奶 | 拍嗝 / 竖抱 | 「让宝宝**打出奶嗝**」「将宝宝**坚起来**」 |
| 宝宝便秘 | 揉腹 | 「顺时针的**揉一揉肚子**」 |

**要点用的是现代标准术语,知识库用的是口语化旧措辞**——`recall` 因此被低估。
**这是评测集的问题,不是被测系统的问题**,而它此前完全不可见。

**② 确定性段 / 生成段分离(留作后续)**

MewHelp 把评测切成三段:检索段(确定性)/ 证据覆盖度(确定性)/ 生成段(LLM),
并支持 `--skip-gen`——**裁判上游挂了也能跑前两段**,产物照落、页面标「生成段未完成」。

EvalFlow 所有指标混在一个 run 里。Ch31 的**覆盖率**部分缓解了(能看出哪些指标没评上),
但**没有「只跑确定性部分」这个模式**。

**③ 同一次评测里 A/B 多配置(留作后续)**

MewHelp 一个脚本跑四策略(vector/bm25/hybrid/hybrid_rerank),**同一批题、同一次跑**。
EvalFlow 一次 run 一个配置,比 dense vs hybrid 要跑两次——**这正是 Ch29 要校验可比性的原因**。

④ **跨文档题的部分分**:「凑齐才 1.00」,把几个要点当一条证据链。EvalFlow 是简单平均,多跳题会高估。

⑤ **产物双份 + 页面只读不重算**:保证「终端跑的和页面看到的必须是同一份」。

#### 这段的面试讲法

> 「我看过另一个自己写的项目怎么做评测——它是**脚本式**的,我是**平台式**的。
> 它有些地方比我严谨:**评测集自检**、**确定性段和生成段分离**、**一次跑多配置**。
> 我采纳了第一条,因为它是**真缺口**——我的 `recall` 也是子串匹配,
> 但从来没有检查过「我写的要点到底能不能在知识库/证据里命中」。
> 补上之后第一次跑就发现两条题的要点和知识库措辞对不上,**分数一直偏低但没人知道为什么**。」

**知道「别人哪里比我好」并且**只吸纳真缺口**——比「我要做得比别人全」成熟。**

## 七、可以深挖（面试追问弹药）

被追问时的展开方向，每条都能讲 3~5 分钟:

- **「评测平台最难的是什么?」** → 不是算分，是让分数**可信**。judge 校准、方差、判错自查。
- **「你怎么知道 LLM 裁判准?」** → 金标准校准出 bias/MAE/Pearson；bias 最可操作。
- **「分数掉了怎么定位?」** → 门禁 → 分桶归因 → 逐条 Diff，三级下钻。
- **「为什么没做 Agent/多轮评测?」** → 见[第六节展开](#展开为什么没做-agent-评测)。
  一句话:**标准答案从「一段文本」变成了「一条路径」，而路径没有唯一正确答案**。
  再补一句:我调研过同域的另一个项目怎么妥协(只比工具集合),以及它的代价。
- **「为什么用 Celery?」** → 评测要调几十次 LLM，同步会超时；发起与执行拆开，
  且进程重启后 running 的 run 不会永久卡死。
- **「DetachedInstanceError 遇到过吗?」** → 遇到过**两次**(Ch10 首现、Ch13 复发)。
  根因:`commit()` 让 ORM 对象 expire + `close()` 让它 detached。
  铁律:**commit 之前先取出普通字段**。
- **「测试怎么隔离?」** → 根 `conftest.py` 顶部(早于任何 backend import)设 `DATABASE_URL`。
  放在 `tests/conftest.py` **不生效**——根 conftest 先加载且顶层就 import 了 `backend.db`。
- **「怎么保证 demo 质量?」** → 92 + 33 测试 + Playwright e2e + CI 工作流。
