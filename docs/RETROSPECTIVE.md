# EvalFlow 复盘

> 一份给面试用的项目叙事。不是功能清单——是「为什么这么做」和「踩过什么」。

## 一、30 秒版

**EvalFlow 是一个 RAG/LLM 评测平台。** 你给它一个评测集(问题 + 期望要点 + 分桶)，
它跑评测、算指标、给 PASS/FAIL 门禁判定，并把「这次比上次好不好、为什么」讲清楚。

它最大的特点不是我写了多少功能，而是——**它评测的对象后来换成了我自己做的另一个 RAG 应用**。
这件事把评测平台的价值从「嘴上说」变成了「实测出来」：接上真实系统后，**并发评测逼出了对方一个
潜伏的并发 bug，评测平台自己也被发现有指标判错**。

（27 章，后端 92 测试 / 前端 33 测试 / Playwright e2e 全绿。）

---

## 二、主线：评测平台的价值不在「算出分数」

**任何一个能调 LLM 的人都能写出「跑一遍、打个分」的脚本。** 那不算平台。

平台的价值在于让分数**可比、可信、可行动**——这三件事，每一件都比「算分」难一个量级。
整个项目就是这个主线的展开。

### 1. 可比 —— 分数必须能横向纵向比

一个分数如果不知道「它是在什么条件下算出来的」，就没有意义。

- **快照机制(Ch09)**：发起评测时把「复现上下文」写进 run——
  知识库版本与哈希、prompt 版本、生成/嵌入模型、数据集哈希、top_k、检索方式。
  历史 run 不受后续改动影响。
- **版本化迁移(Ch14)**：SQLite → PostgreSQL 可切换 + alembic 接管建表，
  存量库用 `stamp head` 收养。**不换默认值**——本地仍 SQLite，零改动。
- **跨系统可复现(Ch26)**：接 baby-ai 后发现一个关键问题——**可复现性有一半在对方系统里**。
  EvalFlow 只记自己这半边，则「这次比上次好」不成立(可能是对方知识库变了)。
  解决办法是让对方暴露 `/api/meta`，把它的版本/模型/检索配置/知识库规模也记进快照。
- **拿不到就显式说「不知道」**：meta 不可达时快照写 `meta_error`，
  详情页警示「本次结果**不可**与历史对比」。
  **静默记空比不记更危险**——它会让人误信可比。

### 2. 可信 —— 指标和裁判本身也要被检验

这是项目里我最看重的一层：**「分数的分数」**。

- **judge 校准(Ch18)**：LLM 当裁判打的 0.8 分凭什么信?人工标金标准 → 对比 →
  出 **bias(系统性偏松/偏严) / MAE / Pearson / n**。bias 最可操作(能直接指导修正)。
- **judge 方差(Ch20)**：多次采样后把方差也存下来，识别「不稳定裁判」。
- **可解释性(Ch18)**：每个分数都能下钻到「证据 + 裁判给的理由」。
- **拒答识别(Ch27)**：库外题靠关键词表机械判定。接 baby-ai 后发现——
  **它明明拒答了，但措辞是「不在我的专业范围内」，词表一个都匹配不上**，判成「没拒答」。
  这是**评测平台自己的缺陷**，评自己的 toy pipeline 永远遇不到(那些回答是我们自己写的，
  措辞天然贴着词表)。

> **「用自己的数据测自己的规则」是自欺**——规则和数据同源，测不出覆盖不足。
> 而且这类失效是**静默的**：不报错，只是分数错。

### 3. 可行动 —— 从「一堆数字」到「一个决定」

- **回归门禁(Ch15)**：绝对阈值(`faithfulness ≥ 0.7`)+ 相对基线回归(较基线最多掉 0.05)。
  两条腿挡「绝对质量差」和「改坏了」。null 指标记「未评」不通过——门槛是「每个指标都得评上且达标」。
- **分桶归因(Ch19)**：门禁说「掉了」，归因说「是库外题掉的」。
- **逐条 Diff(Ch18)**：归因说「库外题掉了」，Diff 说「是『宝宝拉肚子怎么办』这一条」。
- **模型性价比(Ch19)**：把分数和成本摆一起，回答「贵 20 倍值不值」。
- **一键复跑(Ch20)**：按快照重跑，把「可复现」从声明变成按钮。

**这条链**：整体分数看不出问题 → 分桶归因缩小范围 → 逐条 Diff 锁定到具体样本。
这是「可行动」的完整形态。

## 三、三个项目的关系

| 项目 | 角色 | 技术亮点 |
|---|---|---|
| **MewHelp**(电商客服) | Agent 编排 | LangGraph 状态机、**Milvus**、多 MCP Server、微调分类器、LangFuse |
| **baby-ai**(育儿助手) | RAG 管线 | 意图路由 → **混合检索** → 精排降级 → 生成、SSE 流式 |
| **EvalFlow**(本项目) | 评测量化 | 数据集管理、LLM-as-Judge、门禁、归因、可复现 |

**闭环**:做 Agent(MewHelp)、做 RAG(baby-ai)、**再做评测量化它们(EvalFlow)**。
Ch26 把 baby-ai 真正接到了 EvalFlow 上——从「三个并列项目」变成「一个闭环」。

**一个差异化钩子——混合检索我做过三遍，三种实现**:

| 实现 | 在哪 | 特点 |
|---|---|---|
| **Milvus** | MewHelp | 生产级向量库，原生 dense + sparse + hybrid search |
| **chroma + RRF** | baby-ai | 应用层融合，轻量 |
| **手写 BM25 + RRF** | EvalFlow Ch16 | 从公式写起，最轻、最透明 |

面试里能讲清「生产级向量库 vs 应用层融合的取舍」，这是大多数候选人给不出的对比。

**方法论也是同源的**:三个项目都用同一套「先写 spec(决策) → 再写 plan(Task 列表) → 实施 → 同步回文档」，
`docs/superpowers/` 就是这套流程的产物。

## 四、最能讲的四个发现

**都是「接真实系统」才暴露的，评自己的 toy pipeline 一个都遇不到。**

### 1. 并发评测逼出对方一个潜伏的并发 bug

改 baby-ai 一个配置想对比指标，结果**第二次评测直接失败**。日志精确指向
`retriever.py:144` `IndexError`。

对照实验:关改写会挂、**开改写并发也挂** → 证明**跟配置无关**，是早就存在的 bug:
BM25 懒加载非线程安全，并发请求同时看到「还没初始化」就各自跑一遍，
一个线程重建索引数组时另一个正在用它索引。

**手工单点试用永远不会暴露**——只有并发评测会。

### 2. 测出了被测系统的真实短板

baby-ai 的 `faithfulness` 只有 **0.1**。逐条看 trace，它自己都写着
「以下回答基于我的**通用医学知识**」「知识库中**没有相关信息**」——
**检索到了证据却不用它**。这正是 RAG 评测该抓的问题。

### 3. 发现评测平台自己判错了

`rejection` 判 0.0，但人工看 trace 发现 baby-ai **明明拒答了**——见上面「可信」一节。

修的过程还有个反复:第一版词表写「**我**只能回答」，下一跑 baby-ai 说成
「**只能回答**育儿相关问题」(少了个「我」)，**照样漏**。
> 同一个模型换个 run 措辞就会漂，**词表不能贴着某一次的输出写**。

### 4. 导出 CSV 的内存爆炸

样本少时一切正常。算一下才发现：后端把全量 trace + 整份 CSV + 加 BOM 的副本存了 2~3 份，
前端又是 axios 字符串 + Blob + objectURL 再 2~3 份。
**一份 100MB 的 CSV，前后端合计吃 400~600MB。**

改法：后端 `StreamingResponse` + `yield_per`，前端**交给浏览器原生下载**(不碰 JS 内存)。

> 关键判断:**「先攒齐再交付」在数据规模不受控时必然出事**。
> 判据很具体——响应头有 `transfer-encoding: chunked` 才是真流式。

## 五、一条被「用出来」的演进：从界面钻到测量方法

Ch24 之后有一段连续的问题，值得单独讲——因为它展示了**提问深度的爬升**：

| 阶段 | 问的是什么 | 挖出了什么 |
|---|---|---|
| Ch24 | 输入框布局、标签含义 | 分桶不是分组标签，是**评分语义的开关** |
| Ch25 | 数据多了还能下载吗 | 「先攒齐再交付」是内存的敌人 |
| **Ch26** | **能不能评真实系统** | **分水岭**——并发评测逼出对方一个潜伏的并发 bug |
| Ch27 | 它明明拒答了，为什么判 0 分 | **评测平台自己判错了** |
| Ch28 | 阈值 0.7 有什么依据 | **两个方向都错**：高于被测系统实际水平、低于噪声 |

**分水岭是 Ch26。** 在那之前，问题都在「界面层」；接上真实系统之后，问题开始指向**评测方法本身**。

### 后两章的共同主题：怀疑自己的测量工具

- **Ch27**：关键词表匹配不上真实系统的措辞 → **规则和数据同源就测不出覆盖不足**
- **Ch28**：换裁判指标动 0.31，而门禁容忍度只有 0.05 → **先量准仪器，再用它下结论**

这两条都**不是「我实现了什么功能」**，而是「**我发现我的测量方式本身有问题**」。

### 为什么这段在面试里特别值钱

> 一个能写出评测平台的人，和一个**能发现自己评测平台在骗人**的人，不是一个层次。

前者的坑是「做不出来」；后者的坑是「**做出来了但结果是错的，而且不报错**」。
后者更难发现——因为测试全绿、指标算得出来、界面一切正常，
**只有穷究「这个数字凭什么可信」才会暴露**。

而且这两次都是**先怀疑、再实测、最后改掉**：
- Ch27：用 baby-ai 的**真实回答原文**做用例（而不是编一个贴着词表的句子）
- Ch28：先测三个噪声源，再据实校准（而不是继续沿用 0.7）

**面试时的讲法**：
> 「平台跑起来之后，我没停在『指标能出来』，而是继续问『这个指标凭什么可信』。
> 结果发现两件事：我的拒答识别认不出真实系统的措辞；我的门禁容忍度比测量噪声还小——
> 也就是说，**它天天在误报，而我一直以为它在正常工作**。」

## 六、诚实的边界：没做什么，为什么

面试里说清「不做什么」和「为什么」，比列功能更能体现判断力。

| 没做 | 为什么 |
|---|---|
| **SSE 实时进度** | 进度是 Celery worker 写的，要真推送得跨进程上 Redis pub/sub。为「一个进度百分比」不值得；1.5s 轮询够用。**能讲清「为什么这里用轮询而不是 SSE」比真写一段更有价值。** |
| **统计显著性 / 置信区间** | 已识别为必要(5 个样本上 ±0.1 基本是噪声)，但 demo 数据量下用不上。**知道它该做、也知道现在不该做。** |
| **CI 自动评测 + PR 门禁** | 需要 remote + CI 跑真实 LLM(密钥/成本)，且仓库无 remote。工作流已写好待用。 |
| **多租户 / 权限角色** | roadmap 明确排除——Ch12 只做单用户 API key，先解决「防匿名烧钱」。 |
| **接 MewHelp(电商域)** | 域不匹配，要另造一套电商评测集 + judge。**先接同域的 baby-ai，投入产出比高得多。** |

## 七、可以深挖（面试追问弹药）

被追问时的展开方向，每条都能讲 3~5 分钟:

- **「评测平台最难的是什么?」** → 不是算分，是让分数**可信**。judge 校准、方差、判错自查。
- **「你怎么知道 LLM 裁判准?」** → 金标准校准出 bias/MAE/Pearson；bias 最可操作。
- **「分数掉了怎么定位?」** → 门禁 → 分桶归因 → 逐条 Diff，三级下钻。
- **「为什么用 Celery?」** → 评测要调几十次 LLM，同步会超时；发起与执行拆开，
  且进程重启后 running 的 run 不会永久卡死。
- **「DetachedInstanceError 遇到过吗?」** → 遇到过**两次**(Ch10 首现、Ch13 复发)。
  根因:`commit()` 让 ORM 对象 expire + `close()` 让它 detached。
  铁律:**commit 之前先取出普通字段**。
- **「测试怎么隔离?」** → 根 `conftest.py` 顶部(早于任何 backend import)设 `DATABASE_URL`。
  放在 `tests/conftest.py` **不生效**——根 conftest 先加载且顶层就 import 了 `backend.db`。
- **「怎么保证 demo 质量?」** → 92 + 33 测试 + Playwright e2e + CI 工作流。
