# EvalFlow 生产级硬化路线图(Ch09–Ch14)

## 定位

Ch01–Ch08 完成了「最小可用评测平台」的闭环:造评测集 → 跑评测 → 看指标 → 对比配置,并 Docker 一键部署。

这份路线图把 Ch08 复盘时得出的「生产级差距」转成后续章节。核心判断:**当前是「高完成度的教学/demo 级」,离生产级差的不在功能多少,而在「上线才需要」的硬骨头。** 每章对应一块硬骨头,按优先级排序。

> **这份文件是「规划」,不是「待办清单」。** 各章的实际工作由**各自的 plan**
> (`plans/2026-10-10-ch09-*.md` 等)跟踪,下面的条目写的是「各章要达成什么」。
> 用普通列表而非 checkbox,就是为了不让人误以为这里还有没干的事。

## 差距 → 章节映射

| 差距维度 | 章节 | 一句话目标 | 现状问题(代码位置) |
|---|---|---|---|
| 可复现性(评测平台生命线) | **Ch09** | config 快照纳入知识库 / prompt / 模型 / 评测集版本 | `config` 只存 `top_k`;[knowledge.py](backend/knowledge.py) 硬编码 |
| 任务执行模型 | **Ch10** | 评测任务队列化:并发 + 断点续跑 + 进度 | `run_service.execute_run` 串行 `for`;FastAPI `BackgroundTasks` 进程内 |
| LLM 可靠性 | **Ch11** | 重试 / 熔断 + judge 多次采样校准 | [llm.py](backend/llm.py) 无重试;`_judge` 单次打分 |
| 安全与成本 | **Ch12** | 鉴权 + 限流 + 费用统计 | 无鉴权,任何人可发起评测烧 API 费用 |
| 可观测性 | **Ch13** | 结构化日志 + 历史指标趋势 | 无日志框架;`Trace` 有数据但无趋势展示 |
| 数据层与交付 | **Ch14** | PostgreSQL + 迁移 + CI/CD + HTTPS | SQLite 并发写锁;`init_db` 建表无迁移 |

## 每章范围与关键验收

### Ch09 可复现性增强
评测结果要能回答「这次 run 用的是哪版知识库、哪版 prompt、哪个模型、哪批样本」。
- `Run.config` 从 `{"top_k"}` 扩展为含 `knowledge_version` / `prompt_version` / `chat_model` / `embed_model` / 数据集快照(样本数或内容哈希)。
- 知识库加版本标识(显式 version 字段或内容哈希),run 时写入快照。
- judge prompt 加版本号,prompt 改动可追溯。
- 验收:打开任意历史 run,能看到当时的完整「上下文」,可复现。

### Ch10 评测任务队列化
解决「串行慢」+「进程重启后 running 的 run 永久卡死」。
- 引入任务队列(Celery + Redis,或轻量持久化队列),`execute_run` 提交到队列由 worker 消费。
- 样本并发执行(可配并发数),不再一条条串行。
- run 状态可恢复:重启后 `running` 的 run 能续跑或显式标记失败,不永久卡死。
- 进度上报(已完成样本数 / 总数),前端可看进度。
- 验收:同时发起多个 run 并发跑;中途杀进程重启,run 状态正确。

### Ch11 LLM 调用可靠性 + judge 校准
- `chat` / `chat_json` 加重试(指数退避)+ 熔断(连续失败短路)。
- judge 多次采样(如 3 次)取均值,或加一致性校验;judge 失败先重试再记 NULL。
- 降级:LLM 不可用时 run 明确失败并给出原因,而非卡住。
- 验收:LLM 偶发超时/报错时 run 不直接 failed;judge 分数更稳定。

### Ch12 安全与成本
- API key 鉴权(后端中间件校验,前端提供密钥入口),无 key 拒绝访问。
- 限流(防刷评测烧真金白银)。
- 费用统计:填充 `Generation` 表(token / cost),run 汇总总费用并展示。
- 验收:无 key 无法调用;每次 run 能看到费用。

### Ch13 可观测性
- 结构化日志(统一格式 + 关键字段:run_id / trace_id / 耗时)。
- 历史指标趋势:前端折线图展示某指标在不同 run 之间的变化(版本对比的雏形)。
- 可选:指标导出(CSV/JSON)供外部分析。
- 验收:能回答「faithfulness 这几次跑是升还是降」。

### Ch14 数据层与交付硬化
- SQLite → PostgreSQL(可配置,默认仍可 SQLite 本地跑)+ alembic 迁移替代 `init_db`。
- CI/CD(GitHub Actions:后端 pytest + 前端 vitest + 镜像构建)。
- 端到端测试(Playwright 覆盖主流程:造集 → 发评测 → 看结果)。
- 交付加固:HTTPS / compose 健康检查 / 非 root 运行。
- 验收:一键迁移、CI 绿、e2e 覆盖主流程。

## 优先级与理由

1. **Ch09 最优先**:可复现是评测平台「正确性」的根基,且改动独立、不依赖其他章节,收益立竿见影(面试也最常问)。
2. **Ch10 次之**:执行模型是当前最大硬伤(串行 + 进程重启丢任务)。
3. **Ch11 → Ch12 → Ch13 → Ch14**:可靠性 → 安全成本 → 可观测 → 数据层与交付收尾。

## 节奏约定

- 与 Ch01–Ch08 一致:每章**正式开始前**再补该章的 design spec(细化决策)+ plan(Task 清单 + checkbox),实施完同步回两份文档。
- 顺序可按面试准备节奏调整,不必一口气做完——这份 roadmap 只负责「定下全盘、免得忘记」。

## 暂不纳入(超出 demo 量级)

- 多租户 / 权限角色(Ch12 只做单用户 API key,先解决「防匿名烧钱」)。
- K8s / 云原生编排、灰度发布。
- 评测指标的产品化运营(基准集管理、排行榜、回归门禁)。
