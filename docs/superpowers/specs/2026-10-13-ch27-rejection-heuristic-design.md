# EvalFlow Ch27 设计:拒答识别的机械启发式(修 Ch26 暴露的自身缺陷)

## 定位

修**评测平台自己**的一个缺陷——由 Ch26 接真实系统暴露出来。

## 问题

Ch26 评 baby-ai 时,两条库外题的 `rejection` 都判 **0.0**(=没拒答)。但人工看 trace,
baby-ai **明明拒答了**:

> 「抱歉,我只能回答育儿相关问题哦～ 换汽车轮胎属于汽车维修领域,**不在我的专业范围内**」

根因:EvalFlow 的 `rejected()` 是个**关键词表匹配**:

```python
REJECT_MARKERS = ["不清楚", "不知道", "无法回答", "无法提供", "没有相关", "没有证据", "无法给出"]
```

baby-ai 的措辞(「我只能回答…」「不在我的专业范围内」)**一个都匹配不上**。

**这是评测平台自身的误判,不是被测系统的问题。** 评自己的 toy pipeline 永远遇不到——
因为那些回答是我们自己写的,措辞天然对齐词表。

## 决策

### 决策 1:扩词表,并按「意图」分组

```python
REJECT_MARKERS = [
    # 说「不知道 / 没有证据」
    "不清楚", "不知道", "无法回答", "无法提供", "没有相关", "没有证据", "无法给出",
    # 说「超出范围 / 只答某类」(Ch27 新增)
    "我只能回答", "不在我的专业范围", "不是我的专业", "超出我的专业", "超出我的能力范围", "帮不上忙",
]
```

**理由**:这两类措辞语义上都表达「我不答这个」,分开写让人看得懂为什么。

### 决策 2:测试用**真实回答原文**,不用理想化句子

用例直接抄 baby-ai 的实际输出(含 emoji、markdown),而不是编一个「标准拒答句」。

**理由**:编的句子会不自觉地贴着词表写,测了等于没测。**用真实数据才能真的防回归**。

### 决策 3:承认这是启发式,把边界写进 docstring

`rejected()` 的 docstring 明确写:词表覆盖不到的说法一律算「没拒答」(漏判);
换来的是确定性 + 零成本;要更准只能上 LLM judge,但那样就没有「机械基线」的意义了。

**理由**:**不把启发式包装成判定**。使用者必须知道它会在什么时候骗人,才谈得上「知道自己在测什么」。

## 验收

- [x] baby-ai 的两条真实拒答回答 → `rejected()` = 1.0。
- [x] 正常回答仍为 0.0(不引入误判)。
- [x] 离线重算已存 trace:Run 6/8/9 的 6 条库外 trace 全部 0.0/0.5 → 1.0。
- [x] 实跑 Run 10:`rejection` = **1.0**(Run6/8 是 0.0,Run9 中间态 0.5)。
- [x] 后端 92 测试全绿。

## 修正过程(值得记)

第一版词表加的是「**我**只能回答」,**下一跑就漏了**——baby-ai 说成「**只能回答**育儿相关问题」
(少了个「我」)。**同一个模型换个 run 措辞就会漂,词表不能贴着某一次输出写**。
改宽成「只能回答」后覆盖全部。

## 本章不做

- **把 `rejection` 改成 LLM judge**:会引入方差和成本,且失去「机械基线」的定位。
  真要做应是「机械优先 + LLM 兜底」的混合,属于另一个设计。
- **词表可配置化**:接更多外部系统后若确实需要,再抽成 settings。

## 留下的教训

**机械指标对「措辞」极脆**。它在自己的数据上表现完美(因为措辞是自己定的),
一换被测系统就可能整体失效——而且**失效是静默的**(不报错,只是分数错)。

所以:**每接一个新的被测系统,先人工看它实际怎么说话**,再决定词表够不够。
这也是 Ch26 那条「换了系统才暴露」的具体例子。
