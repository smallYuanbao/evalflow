# EvalFlow Ch24 设计:交互细节再修

## 定位

第二轮逐页复查发现的问题,分三类:

- **语义 bug**:分桶可为空导致打分方式错、基线自动默认写脏 URL。
- **功能缺失**:金标准标了之后无法清空。
- **可用性**:输入框宽度/计数遮挡、指标名没有释义。

## 决策

### 决策 1:分桶改必选——它不是「分组标签」,是**评分语义的开关**

`run_service` 里判断库外题用的是 `bucket == "库外"`(精确匹配):

```python
judges = [] if bucket == ABSENT_BUCKET else [...4 个 judge...]
if bucket == ABSENT_BUCKET: s.add(Score(name="rejection", ...))
else:                       s.add(Score(name="recall", ...))
```

**分桶为空 → 被当成「库内题」→ 用 recall + 5 个 judge 去评一道库外题**——它的正确行为本该是**拒答**,却被按「必须答对」来打分。分数直接失真。

所以分桶不是可有可无的元数据。改为必选:未选时按钮禁用 + 提示「影响打分方式」。

### 决策 2:自动默认的基线**不写 URL**,只有用户显式选择才写

拆成两个来源:

- `urlBaseline`——URL 里的,代表**用户显式选的**(可分享、刷新不丢)
- `autoBaseline`——自动挑的默认值(紧邻的上一次),**只存内存**

`baselineId = urlBaseline ?? autoBaseline`。用户一旦在 select 里动手,清掉 `autoBaseline` 并把选择写进 URL。

**理由**:URL 是**用户意图**的记录。只是打开一个 run 页,地址栏就被塞上 `?baseline=4`,用户没做任何选择却看到地址变了——这是「系统把自己的默认值伪装成用户的决定」。

### 决策 3:基线选择器加标签(真正的困惑点)

用户反馈:「点 Run #5 的查看,为什么右边的 Select 默认选中 Run #4?不应该选中 Run #5 吗?」

**这不是 bug,是 UI 没说清**——那个 Select 选的是「**拿谁当对比基准**」,不是「当前查看的 run」。#5 的基准是 #4 是对的(拿 #5 跟自己比没有意义)。但 Select **没有标签**,只显示一个 `Run #4 (done) · 育儿-常见病`,用户自然会把它读成「当前 run」。

**修法**:加可见标签「对比基线」+ 悬停解释它是什么。含义不该藏在下边一行小灰字里。

> 注:上一轮以为用户质疑的是「URL 被自动改写」,改成了「只有显式选择才写 URL」。那个改动本身是对的(URL 不该混进系统默认值),但**没解决这次的实际困惑**——困惑来自选择器缺标签。

### 决策 4:CSV 表头改中文

CSV 是**后端**产出的,所以中文列名加在 `backend/metrics.py` 的 `METRIC_LABELS`,由 `run_export_csv` 使用。

**代价(要记着)**:指标中文名现在**存在两份**——后端 `metrics.py`(供 CSV)和前端 `utils/metrics.ts`(供界面)。它们服务不同层,不好共用;在两边都留了注释提醒同步,加指标时别只改一处。

### 决策 5:指标名加释义,并把重复的 `METRIC_LABELS` 收敛到一处

「召回(机械)」和「上下文召回」光看名字分不清(一个是机械子串匹配,一个是 LLM 裁判)。抽出 `utils/metrics.ts`,含 `METRIC_LABELS` + `METRIC_DESC`,在关键位置(tooltip)露出解释。

**顺带**:原先 4 个视图各抄一份 `METRIC_LABELS`,加指标要改 4 处。收敛成单一来源。
