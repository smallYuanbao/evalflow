# EvalFlow Ch32 设计:评测集自检

## 定位

补一个**真缺口**,由「和 MewHelp 的评测做对比」引出。

`recall` 是机械子串匹配——`expected_output` 的要点只要**不是逐字**出现在检索证据里就判 0。
「物理降温」和「温水擦浴」语义相同,字面不同,分数天差地别。

**后果是静默的**:评测集写错了不会报错,只会让分数莫名偏低——
你会以为是系统检索差,**其实是评测集的措辞和知识库对不上**。

这和 [Ch27](../pitfalls/ch27-heuristic-brittleness.md)「用自己的数据测自己的规则」是同一个病:
**错在尺子,怪在被测对象。**

## 参照

MewHelp 的 `validate_eval_ch04.py`,原话:

> 「300 题手写的 ground truth **靠这个脚本兜住,不靠人眼**」

它查五件事,其中一条正中 EvalFlow 软肋:**`expect_points` 必须逐字出现在知识库正文里**。

**适配差异**:MewHelp 知道自己的知识库;EvalFlow 的被测系统可能是外部的(baby-ai),
拿不到对方的知识库——改用**已经跑过的 run 的检索证据**来代替。

## 决策

### 决策 1:两层检查,结构检查不需要跑过评测

- **结构检查**(总是做,纯数据层面):空要点 / 空分桶 / 库外题带要点 / 问题重复 / 要点有空项
- **证据检查**(传 `run_id` 时做):拿该 run 实际检索到的证据比对要点

**理由**:结构问题**在跑之前就该发现**,不该等到跑完看分数才发现异常。

### 决策 2:只报「全部要点都没命中」,且定级 warning

证据检查只报「该题**所有**要点都没在证据里逐字出现」的——那是最强的信号。
**定 warning 而非 error**:也可能是检索确实没找到,由人判断。

同时给一条 `info` 级的**总体命中率**(如「14/16 条能命中」),便于区分
「个别题写错」还是「整体措辞体系对不上」。

### 决策 3:端点在数据集上,不是 run 上

`GET /datasets/{id}/validate?run_id=`
—— 自检的对象是**评测集**,run 只是可选的比对依据。

## 实测:第一次跑就抓到真问题

```
错误 0 / 警告 2
⚠ item17 「宝宝便秘怎么办」要点 揉腹/纤维/就医 全部没命中
⚠ item18 「宝宝吐奶怎么办」要点 拍嗝/竖抱/生理性 全部没命中
ℹ 该 run 覆盖 16 条库内题,其中 14 条的要点能在证据里命中 (88%)
```

| 题 | 期望要点 | 证据里的实际措辞 |
|---|---|---|
| 宝宝吐奶 | 拍嗝 / 竖抱 | 「让宝宝**打出奶嗝**」「将宝宝**坚起来**」 |
| 宝宝便秘 | 揉腹 | 「顺时针的**揉一揉肚子**」 |

**要点用现代标准术语,知识库用口语化旧措辞** → `recall` 被低估。
**这是评测集的问题,不是被测系统的问题**,此前完全不可见。

## 本章不做(留作后续)

- **确定性段 / 生成段分离**(MewHelp 的三段式 + `--skip-gen`):EvalFlow 的覆盖率部分缓解了,
  但「只跑确定性部分」是结构性改动。
- **同一次评测跑多配置**:会改动 run 的模型,留作后续。
- **跨文档题的部分分**「凑齐才 1.00」。
