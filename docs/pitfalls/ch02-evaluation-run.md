# Ch02 踩坑:评测主流程 + LLM judge

> 这一章接通第一条真实评测链:run 生命周期 + LLM judge + 分桶聚合。坑都在「怎么让 LLM 打分可信、可重放」。

## 坑 1:judge 温度必须固定 0

**现象**:同一份证据 + 同一个答案,两次打分不一样(跳分),平台分数不可复现。

**根因**:LLM 生成有采样随机性,`temperature` 越高越随机。评分是**确定性任务**,容不得随机。

**修法**:judge 调用统一 `temperature=0.0`。

```python
raw = llm.chat_json([{"role": "user", "content": prompt}], temperature=0.0)
```

**原理**:区分两类 LLM 用途——**生成**(写回答,可有一点创造性)和**评判**(打分,必须确定性)。judge 属于后者,温度 0 是铁律。

## 坑 2:judge 失败记 NULL,不记 0(延续 Ch01 坑 4)

**现象**:judge 调 LLM 偶尔会挂(超时/JSON 解析失败/限流)。挂了如果记 0 分,会把这条样本拉成「质量差」。

**根因**:「没评上」≠「零分」。

**修法**:`chat_json` 解析失败返回 `None`,写库时 `Score.value=None, comment="judge 失败"`;聚合时跳过 NULL。

**原理**:单条 judge 挂只让该条 score 记 NULL、继续下一条,**不算 run 失败**;只有 run 级异常才置 failed。这是「失败隔离」:judge 的偶发故障不能拖垮整个 run 的状态。

## 坑 3:recall 是子串匹配,seed 数据措辞要对齐

**现象**:recall(要点召回)测出来偏低甚至为 0,明明是相关证据。

**根因**:本项目的 recall 是**机械子串匹配**——看 `expected_output` 的每个要点是否出现在检索证据 `text` 里。如果 seed 数据里 `text` 的措辞和要点对不上,子串就匹配不上。

**修法**:seed 时让 `text` 的措辞和 `expected_output` 要点对齐(例如要点是「出牙/睡眠倒退/环境」,text 里就出现「出牙、睡眠倒退或环境不适」)。

**原理**:机械基线(recall)和 LLM judge 是**分层**的——能确定的用机械匹配(便宜、可复现),语义的才上 LLM。用机械匹配就要接受它对措辞敏感,测试数据得配合。

## 坑 4:库外题不能硬塞 recall

**现象**:知识库里没有答案的「库外题」,正确行为是**拒答**,此时 recall=0 是「正确拒答」,不是「失败」。硬把库外题塞进 recall 分桶,会误报成「召回差」。

**根因**:指标语义错配——recall 衡量「该找的要点找到了没」,库外题根本没有要点可找。

**修法**:库外题**单独用「拒答率」指标**(机械关键词判断是否拒答),不进 recall 分桶。

**原理**:不同 bucket 的样本,「正确」的定义不同,要用不同的指标衡量。这是评测系统设计的关键:先分桶,再按桶配指标。
