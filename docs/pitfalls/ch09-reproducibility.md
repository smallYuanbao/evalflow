# Ch09 踩坑:可复现性(配置快照)

> 这一章给 run 加「复现上下文」快照:top_k、知识库/prompt 版本、模型、数据集哈希。坑主要是**向后兼容**。

## 坑 1:老 run 没有快照字段,前端不能崩

**现象**:加了快照后,老数据(没有 `knowledge_version`/`dataset_hash` 等字段)的 run 在「复现上下文」卡片里显示 `undefined` 或直接报错。

**根因**:快照是新字段,历史 run 的 config 里没有。前端直接取 `cfg.knowledge_hash` 会得到 `undefined`。

**修法**:前端展示时对每个字段做「缺省显示 `—`」的兜底:

```tsx
<Descriptions.Item label="知识库哈希">{cfg.knowledge_hash ?? "—"}</Descriptions.Item>
```

**原理**:**加字段永远要考虑老数据**。数据迁移的两种成本——要么给老数据回填默认值(后端),要么读取端做缺失兜底(前端)。这里选前端兜底,因为快照只影响展示、不影响计算,回填没必要。

## 坑 2:config 字符串解析要容错(延续 Ch06)

**现象**:`config_top_k` 读老 run 的 config 时,老数据可能是空串 `""`、缺 `top_k` 字段或坏 JSON,直接解析会炸。

**根因**:同 Ch06——历史数据 + 用户输入不可信。

**修法**:`try/except` 回退默认 2(见 Ch06 的 `config_top_k` 实现)。

**原理**:这条和 Ch06 是同一个坑的两次出现,说明「读配置/历史数据要容错」是贯穿性的纪律,值得单独拎出来记。

## 小结

这一章坑少,核心就一条:**加字段/加功能时,老数据怎么平滑过渡**(前端兜底 vs 后端回填)。做「可复现」这种给旧系统增强度的功能,向后兼容是设计的一部分,不是事后补丁。
