# Ch21 踩坑:接口性能(知识库地图超时)

> 这一章是「用起来才发现」的性能问题:知识库页面一进去就卡 35 秒、首次还报超时。根因不是算法慢,是**在请求里做了不该做的事**——全表扫描 + 无缓存 + 同步阻塞。

## 坑 1:请求里全表扫描 + 每次重算,35 秒超时

**现象**:第一次进「知识库」页,接口要么转很久、要么直接「加载失败」;之后每次进也干等几十秒。实测 `GET /knowledge/map` 耗时 **35.0 秒**。

**根因**:三件事叠加(原 [main.py](../../backend/main.py) 的 `knowledge_map`):

```python
inputs = [it.input for it in s.query(DatasetItem).all()]  # ① 抓整张表(实测 697 条)
chunk_vecs = embed([k["text"] for k in KNOWLEDGE])        # ② 每次重新嵌入静态知识库
query_pts = project(embed(inputs), mean, basis)           # ③ 全部 input 一次性发 Ollama
```

- **① 查询无界**:`DatasetItem.query.all()` 是**所有评测集的所有样本**,不是「相关的那些」。样本随使用累积(dev 库和测试共用 `data/eval.db`,堆到 697 条),耗时线性增长。
- **② 无缓存**:知识库 23 条 chunk 是**写死的静态数据**,却每次请求都重新 embedding + 重算 PCA。
- **③ 同步阻塞**:整条链路跑在请求处理器里,全程占一个线程。

实测耗时分布:23 条知识块 **3.1s**,697 条样本 **28.1s**,合计 **35s**。而 embedding 超时是 60s——**为什么「第一次」才报超时**:首次进页面时 Ollama 的 bge-m3 可能还没载入内存(冷启动)要额外几秒,冷启动 + 35s **越过 60s 超时线** → 抛 `ReadTimeout` → 前端报错;之后再进模型已热(35s < 60s),不报错了,但还是干等 35 秒。

**修法**:拆成 [knowledge_map.py](../../backend/knowledge_map.py),三条对症:

1. **静态部分缓存**:知识库的 chunk embedding / PCA 基底 / chunk 坐标只算一次,存模块级变量,后续请求共用(知识库不变,没理由重算)。
2. **样本部分有界**:`_recent_unique_inputs(limit)` 只取**最近 N 条去重**的样本问题。地图是给人眼看散点的,697 个点挤一起既慢又**看不清**,取 100 条足够。
3. **超时可配 + 放宽**:`EMBED_TIMEOUT` 默认 120s,给冷启动 + 批量留余量。

效果:**35s → 冷缓存 8s、缓存命中 0.7s**。

**原理**:**「每次请求都重算不变的量」是把静态成本变成了动态成本**。凡是「输入不随请求变、输出不随请求变」的计算(静态知识库的 embedding、PCA 基底、字典/配置),都该算一次缓存住。另一半是**「可视化不需要全量数据」**——散点图的信息密度有上限,给它 100 个点还是 700 个点,人眼看到的结论一样,但代价差 7 倍。性能优化第一步往往是「这个请求真的需要这么多数据吗」,而不是「怎么算得更快」。

## 坑 2:函数内给全局变量赋值忘写 `global`

**现象**:修完上面三处,接口从 35s 降到 0.2s——但返回 `500`,日志 `UnboundLocalError: cannot access local variable '_chunk_cache' where it is not associated with a value`。

**根因**:Python 的作用域规则——**函数内只要对某名字有赋值,该名字在整个函数体里就被当作局部变量**,读取会发生在赋值之前的 `if _chunk_cache is None:` 上,于是「访问了还没赋值的局部变量」。

```python
_chunk_cache = None
def _chunk_layout():
    if _chunk_cache is None:      # ← 期望读全局,实际读的是(尚未赋值的)局部
        _chunk_cache = {...}      # ← 这一行让 _chunk_cache 变成局部
```

**修法**:函数开头声明 `global _chunk_cache`。

**原理**:这是「模块级可变状态」绕不开的代价——好处是简单(不用引入缓存框架),代价是要显式告诉 Python「我改的是全局那个」。换个思路也可以把缓存收进一个类实例或 `functools.lru_cache`,但小场景下一个 `global` 加一句注释更直白。

## 小结

这一章收敛成两句:**「不变的量别每次重算,要看的图别喂全量数据」**——前者是缓存意识,后者是「先问需要多少数据」。附带一个 Python 作用域的老坑:模块级缓存函数里想改全局,记得写 `global`。

性能问题的诊断顺序也值得记:先**量**(实测 35s、拆成 3.1s + 28.1s),再**定位**(28.1s 在样本 embedding),最后**对症**(缓存 + 有界),而不是凭感觉猜「是不是 Ollama 慢」。
