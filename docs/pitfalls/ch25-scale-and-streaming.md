# Ch25 踩坑:被忽略的「数据规模」维度

> 这一章不是「代码写错了」,是**功能在 demo 数据量下正确、数据量一大就崩**。导出 CSV 就是个典型:样本几条时怎么都对,十万条时前后端一起爆内存。记录它,是为了以后新加「导出/批量/大列表」这类功能时先想一下规模。

## 坑 1:两端各把整份文件缓冲 2~3 份

**现象**:导出 CSV 在样本少时正常;样本上万后页面点下去**卡住没有任何反馈**(看起来像死了),再多直接 OOM。

**根因**:「拼好整份内容再交给对方」的写法,在前后端各存了好几份。

后端:
```python
traces = s.query(Trace).filter(...).all()   # ① 全量 ORM 对象(含 output 正文)
buf = io.StringIO()                          # ② 整份 CSV 字符串
return buf.getvalue()
content="﻿" + csv_text                  # ③ 加 BOM 又复制一份
```

前端:
```js
const csv = await api.exportRunCsv(id)   // ① axios 把整个响应读成 JS 字符串
const blob = new Blob([csv], ...)        // ② 复制一份
URL.createObjectURL(blob)                // ③ 再持有
```

一份 100MB 的 CSV,前后端合计要吃 400~600MB。而且 `new Blob([巨串])` 跑在**主线程**,直接冻结 UI——所以是「页面卡死」而不是「转圈等待」。

**修法**:
- 后端 `StreamingResponse` + SQLAlchemy `yield_per(500)`:逐行产出,内存从 O(全部) 降到 O(一批)。
- 前端**不做 Blob**,直接让浏览器下载(`<a href=接口>`):浏览器原生流式落盘,零 JS 内存,还自带进度条和取消。

验证:响应头出现 `transfer-encoding: chunked` 就是真流式(而不是攒完再发)。

**原理**:**「先攒齐再交付」是内存的敌人**。只要数据规模不受控,就该走流式——生成端边算边发、消费端边收边落盘,两端的驻留量都与总量解耦。判断标准很简单:问一句「这份数据最大能有多大」,答不上来或者答案是「很大」,就该流式。

## 坑 2:`Content-Disposition` 设了却没用——绕开浏览器反而更差

**现象**:后端早就返回 `Content-Disposition: attachment`,前端却用 axios 拉文本 + Blob 自己造下载。

**根因**:前端「自己拼下载」看起来更可控(能带鉴权头、能自定义文件名),实际上**放弃了浏览器白送的流式下载能力**,把整份文件拽进 JS 内存。而那个 header 本来就是为「让浏览器自己处理」准备的。

**修法**:前端改成 `<a href=接口>` 触发。

**代价要认**:导航请求**带不上自定义头**,所以鉴权时改用 `?token=` 查询参数——只有导出这一个只读端点开这个口子。

**原理**:平台已经提供的能力,先想想能不能直接用,别急着在自己这层重造。重造往往丢掉的正是平台已经解决好的问题(流式、进度、取消、大文件)。

## 小结

两句话:**「先攒齐再交付」在数据规模不受控时必然出事,该流式就流式**;「平台已经给的能力(浏览器原生下载)别绕开,绕开等于放弃了它替你解决的难题」。附带一个具体判据:**响应头有 `transfer-encoding: chunked` 才是真流式**。

诊断这类问题的顺序:**先问「最大能有多大」→ 算内存倍数 → 顺着链路找「在哪里攒的」**。这次是「后端 StringIO 一份 + 加 BOM 又一份 + 前端字符串一份 + Blob 又一份」——每一处单看都合理,叠起来就是 4~6 倍。
