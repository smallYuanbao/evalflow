# Ch28 踩坑:裁判的方差比你想的大得多

> 这一章不是「代码写错了」,是**测量仪器本身有噪声**。做评测的人容易只看被测系统,
> 忘了「打分的那把尺子」也在抖。

## 坑 1:换裁判,指标动 0.39 —— 而门禁容忍度只有 0.05

**做法**:从数据库取出 Run 10 已存的 trace(问题/回答/证据),用**另一个模型族**的裁判
(通义 qwen3.8-max)重打一遍分,和原裁判(deepseek-chat)对比。

**输入完全相同**,所以差异只可能来自裁判。

**结果**:

| 指标 | deepseek-chat | qwen3.8-max | Δ |
|---|---|---|---|
| **context_recall** | 0.5000 | 0.8900 | **+0.39** |
| answer_relevance | 0.6000 | 0.4500 | −0.15 |
| faithfulness | 0.1000 | 0.2333 | +0.13 |

单样本最大波动 **0.5**(「宝宝咳嗽有痰」的 answer_relevance 从 0.9 → 0.45)。

**而 EvalFlow 门禁的 `max_regression` 是 0.05。** 裁判方差是容忍度的 **7.8 倍**。

**后果**:如果两次 run 之间换了裁判,门禁会报出一个巨大的「回归」——而它跟质量毫无关系。
**门禁是用来做发布决定的,它的输入却带着 0.39 量级的噪声。**

**修法(方向)**:① 把裁判模型写进 run 快照(换裁判 = 换仪器,必须记);
② 门禁容忍度要先测出裁判方差再定,不能拍 0.05;③ 裁判可与生成分开配置,便于交叉验证。

**原理**:**一个测量的可信度,上限由仪器的噪声决定。** 你花大力气保证被测系统的输入一致、
快照完整、流程可复现——但如果打分的那把尺子换个牌子就差 0.39,前面那些严谨都被这把尺子吃掉了。

**做评测的人最容易忽略的一层**:盯着被测对象,忘了自己的仪器。

## 坑 2:对比实验里「没对齐的细节」会污染结论

第一次跑 A/B,通义**全部返回空**。查了半天才发现两个独立问题:

**一是没对齐 JSON mode**:原 `chat_json` 带 `response_format={"type":"json_object"}`,
我的替换脚本没带——即使能跑通,**这个对比也已经被污染了**(混进了「有没有强制 JSON」这个变量)。

**二是自己的低级错误**:编辑时去掉函数内的 `import json`,而模块顶部没导入,
于是 `json.loads` 抛 `NameError` —— 被 `_judge` 的 `except Exception` **静默吞掉**,表现为「裁判返回空」。

**修法**:① 替换实现必须和原实现**逐项对齐**(JSON mode、失败返回 None、温度);
② **别用裸 `except Exception` 吞掉一切**——它会把「代码 bug」伪装成「模型不配合」。

**原理**:**做 A/B 的前提是「只有一个变量」**。任何没对齐的细节,都让结论失效——
而且它不会报错,只会让结果看起来「有点怪」。
另外:**宽泛的异常捕获会让调试变成猜谜**。吞异常是为了容错,但连 `NameError` 都吞,
就把「我自己写错了」变成了「模型不行」。

## 小结

三句:**① 测量仪器本身有噪声,而且往往比你关心的信号还大**;
**② A/B 的前提是「只有一个变量」,没对齐的细节会静默污染结论**;
**③ 别让宽泛的异常捕获把代码 bug 伪装成外部故障**。

诊断顺序:**先对齐(逐项核对两次调用),再测量,最后才解读差异**。
